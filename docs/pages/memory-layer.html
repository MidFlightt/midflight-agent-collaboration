Midflight Memory Layer

Everything agents tell Midflight, and everything it tells them back, lives behind one interface: the Store. This page shows where that state sits, how a write stays safe when four agents act at once, and how the FalkorDB graph finds which agents a plan change reaches.

Writes

Every change is one atomic commit

Services never save entities one by one. They build a Commit and hand it to the store, which writes all of it or none of it. A claim and its review job go in the same commit, so accepted work can't lose its job.

What a Commit carries

  • project_idEvery entity in the commit must belong to this project.
  • putsThe entities to save: claims, plans, directives, jobs, escalations…
  • auditAudit events saved in the same write.
  • expected_coord_revCompare-and-set on the project's revision. If another agent changed the project first, nothing is written and the store raises RevisionConflict; the service re-reads and reviews again.
  • bump_coord_revEvery claim or plan change increments the revision.
  • idempotency_keyA retried commit with the same key writes nothing and returns duplicate=True.

How FalkorStore decides, inside one query

A CASE picks the first outcome that applies. The writes run in a FOREACH only when the outcome is ok. No Python lock and no pre-read decides it.

  1. Idempotency key used by another projectValueError
  2. Idempotency key already appliedduplicate, no write
  3. coord_rev moved since the caller read itRevisionConflict
  4. Project doesn't exist and isn't being createdLookupError
  5. Analyzed plan graph changed before approvalGraphChanged
  6. An entity id belongs to another projectValueError
  7. Approved plan would changeValueError
  8. Saved claim revision would be editedValueError
  9. Write everything, bump revision, save receiptapplied

What's stored

The graph inside FalkorDB

Each entity is a node with its full model saved as canonical JSON in payload, and simple fields copied out so they can be indexed. Approving a plan also writes a projection of it: one node per task, contract and requirement, joined by the edges that say who provides and who consumes what.

Claims are revised, never editedEach change saves a new revision under (id, revision). Only the verdict fields, state and findings, can change on a saved revision.
Approved plans are frozenChanging the plan means proposing a new version. The store refuses any edit to an approved one.
The audit log only growsEvery commit's events are appended, so you can replay what each agent declared and when.

Sequence

What happens when the lead approves a plan

PlanService uses the graph when the store offers it (the optional GraphPlanStore protocol), and the direct rule in domain/impact.py otherwise.

  1. Read the project and the draftRecompute the changed ids between the plan in force and the draft.
  2. Walk both plan graphsThe proposed graph must match the draft just read. If the draft changed in between, re-read and retry.
  3. Build the changesA directive for each affected task, with the graph path in its reason. Older open directives for those tasks are superseded. Affected approved claims go back to pending with a fresh review job. Everything else is untouched.
  4. Write it in one guarded commitThe query checks the project revision and each analyzed graph snapshot, then saves the approval, directives, claims, jobs and audit events together.
  5. Only then wake the workerA second, competing approval gets a conflict and never dispatches the jobs it built locally.
Reading it back

What an agent gets at a check-in

Agents call check_in at their checkpoints. Everything in a reply stays in the agent's context and costs tokens on every later step, so each reply carries a marker like checkout.20261017T091233Z. Pass it back as since and the reply leaves out what that earlier one already held (D34).

First check-inno since
  • Task requirements and contractssent
  • Claim verdictsent
  • Open directives, with graph evidencesent
  • What other tasks' claims assume about this onesent
  • Decisions and open escalationssent
  • ready_to_push and push blockerssent
  • Marker for next timesent
Later check-insince=checkout.20261017T091233Z
  • Task requirements and contractsonly ids that changed
  • Claim verdictsent
  • Open directivessent
  • Neighbours' assumptionsonly new ones
  • Decisionsonly new ones
  • ready_to_push and push blockerssent
  • New markersent

The marker belongs to the conversation, not the account. Two sessions signed in as one person never hide anything from each other, and a session that lost its context sends no marker and gets everything. Directive evidence is read from the saved reason, so no graph query runs at delivery time.

Limits

What to keep in mind

Memory forgets on restartMemoryStore keeps everything in process. It's for tests and laptops, and it has no graph queries.
Multi-hop impact is FalkorDB onlyMemory and DynamoDB send directives only to tasks that touch the changed item directly.
One worker per graphRecoverableWorker runs jobs at least once and has no distributed lease, so run exactly one service process against a graph.
Production is still DynamoDBThe FalkorDB store is the Graph Hacks build. The AWS deployment hasn't moved.
